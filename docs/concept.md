# SHIOKONBU Pet 構想 v1.0

pet.shiokonbu.com の中長期方針（Nori 2026-11-02）。
「構想を見直そう」と言われたら、この文書全体を見直す。新しい発見・ユーザーニーズ・競合・技術変化・事業者からの声に応じて更新し、版と日付を下の「更新の記録」に足す。

**作業ルール**：提案・作業・PR・引き継ぎ・作業ログでは、最初に [A]〜[G] のどれの話かを書く。
例：`[B] SEO：千葉県ペットタクシーページ改善` / `[B] SNS：寝たきり犬の移動に関する投稿企画` / `[C] DB：大型犬・車両情報項目追加` / `[D] 検証：ペットタクシー10社入力` / `[E] マッチング：最短お迎え時刻ロジック` / `[F] 収益化：事業者向け月額機能の仮説` / `[G] 並列化：SEO・DB・事業者調査を同時進行`。
作業を提案するときは「ほかの作業が終わるまで待つ必要があるか、今すぐ並行できるか」を判断する。**待つ理由がなければ並行して進める。**

## [A] 北極星

pet.shiokonbu.com は、単なるペットタクシー比較サイトではなく、

> 地域のペットサービスを標準化し、正確な供給情報と需要をつなぐ「データ基盤＋マッチング＋送客インフラ」

を目指す。

ペットタクシーを上位概念にしない。pet.shiokonbu.com 自体を「地域のペットサービスを探すための基盤」と位置づけ、その中に独立したカテゴリが並列にある構造にする。

- 移動：ペットタクシー、通院送迎、長距離移動
- 在宅ケア：老犬・シニア犬の訪問介護、寝たきり犬の介助、ペットシッター
- 行動・教育：出張ドッグトレーナー、問題行動対応
- 美容・生活：訪問トリミング、ペットホテル

共通の問題は「地域ごとに事業者が分散し、料金・条件・対応範囲などが標準化されておらず、比較・判断しにくい」こと。SHIOKONBU はここを標準化する。

目指す価値は **「おすすめランキング」ではなく、「あなたの条件なら、この事業者が利用可能」と判断できること**。

## [B] 足元の集客

[A] は長期構想。いまはユーザー・事業者ともまだ十分に集まっていないので、SEO・SNS・検索流入・認知拡大を強く進める（SEO、SNS、地域ページ、サービスページ、ガイド記事、内部リンク、インデックス改善、CTR改善、検索順位改善、SNS投稿、ブランド認知）。

SEO記事も将来の事業構造につながるものを優先し、**地域 × 条件 × 利用目的** を重視する。
例：千葉県のペットタクシー／大型犬を運べるペットタクシー／歩けない犬を病院へ運ぶ方法／千葉県の老犬訪問介護／寝たきり犬の在宅介護／千葉県の出張ドッグトレーナー／大型犬対応の訪問トリミング。

SEOで集めたユーザーを、将来の **比較 → 条件検索 → マッチング → 事業者発見** へつなげる。
SNSも単なるフォロワー増加ではなく、「地域のペットサービスを探すならSHIOKONBU」という認知につなげる。

## [C] 今作るプロダクト

**運営内部用の事業者管理画面＋構造化DB** を作る。いまは事業者自身には開放しない。
最初はペットタクシー中心でよいが、訪問介護・出張ドッグトレーナー・訪問トリミングなどへ広げられる設計にする。DBは **共通項目＋サービス固有項目** に分ける。

- 共通項目：事業者名、サービス種別、対応地域、営業時間、料金体系、支払い方法、キャンセル規定、保険、資格、情報取得元、最終確認日、事業者本人確認状態
- ペットタクシー固有：基本料金、距離料金、迎車料金、待機料金、深夜・早朝料金、当日追加料金、出発拠点、最大対応距離、車種、車両サイズ、最大対応体重、大型犬・超大型犬対応、多頭対応、飼い主同乗人数、クレート条件、ストレッチャー、担架、スロープ、リフト、介助対応、当日予約可否
- 訪問介護固有：寝たきり対応、排泄介助、食事介助、投薬補助、大型犬介助、夜間対応、訪問可能時間、対応可能体重、資格等
- 出張トレーナー固有：対応犬種、対応体重、吠え、噛み、引っ張り、分離不安、パピー対応、トレーニング方針、出張範囲、初回料金、継続料金、最短予約可能日

できるだけ **Boolean / 数値 / enum / 日時 / 位置情報** など、検索・計算できる形で持つ。自由記述だけにしない。可能なら耐荷重・サイズも持つ。

## [D] 実データで検証する

最初から完成形を作り込まない。まずペットタクシーを中心に **20〜30社を運営側で実際に入力** し、取得できない情報・事業者ごとに定義が違う項目・本当に必要な比較項目・マッチングに効く項目・不要な項目・足りない項目を確かめる。

DBを作る → 実データを入れる → 問題を見つける → DBを直す、をくり返す。
20〜30社が全部終わるまで他を止めない。5社・10社の段階でも、検索UI・条件マッチング・SEOへの活用・ユーザー導線を試す。

## [E] 次の競争優位

静的な料金・サービス情報だけなら、将来AIが各社サイトから直接取れる。SHIOKONBU は **「今、本当に利用できるか」** まで扱う。

ペットタクシーでは、今日対応できるか・何時から・車両の空き時間・出発地点・お迎え地点・準備時間・移動時間・対応できる犬の状態を組み合わせて **最短お迎え可能時刻** を計算できる状態を目指す。

例：現在10:00、準備30分、迎え先まで45分、バッファ15分 → 最短11:30から対応可能。

さらに「50kg・セントバーナード・歩行困難・ストレッチャー必要・飼い主2名・今日15時まで」のような条件で、**本当に対応できる事業者だけを返す**。

### AI対応

AIに「今日、50kgの歩けない犬を病院まで運べるところを探して」と頼む世界を前提にする。目的はDBを丸ごと渡すことではなく、**AIに SHIOKONBU の検索・マッチング機能を使わせること**。将来の機能の例：

- `find_providers`：条件に合う事業者を探す
- `check_availability`：空き状況や最短対応時刻を調べる
- `contact_provider`：SHIOKONBU 経由の問い合わせへ進む

### Webアクチュエーション

APIだけでなく、AIがふつうのWebサイトを直接操作することも前提にする。条件入力 → 検索 → 比較 → 空き確認 → 問い合わせ まで、人にもAIにも安定して操作できるWeb UIにする。
理想は「AIが各事業者サイトを10社まわるより、SHIOKONBU を1回使ったほうが速く・正確で・最新」。

### AIへの情報公開レイヤー

| 層 | 中身 |
|---|---|
| 公開 | 料金概要、対応地域、大型犬対応、サービス概要、掲載情報確認状態 |
| マッチング経由で返す | 現在の空き、最短対応時刻、詳細条件の適合、利用可否、見積もり条件 |
| 非公開 | 内部スコア、運営メモ、需要データ、管理情報、DB全件 |

### 掲載情報確認済み

事業者本人から情報の提供・確認を受けたら「SHIOKONBU 掲載情報確認済み」などを表示する。**優良事業者の認定ではない**。意味は「この情報は事業者本人から提供または確認されています」。将来は料金確認済み・車両確認済み・保険確認済み・資格確認済みなどに分けることも考える。お金を払えば付くバッジにはしない。

## [F] マネタイズ

収益モデルはいま固定しない。**「初回予約成果課金」を前提に全システムを設計しない。**
候補：問い合わせ成果課金、初回予約成果課金、事業者向け月額、空き状況管理、予約管理、事業者向け分析、需要データ提供、API／マッチング利用料、掲載強化、SaaS機能。
どれを中心にするかは、ユーザー利用状況＋事業者ニーズ＋送客実績＋蓄積データを見て決める。いまは価値のある供給データとマッチング基盤を作ることを優先する。

## [G] AI前提の実行モデル

人だけで進めると SEO → データ収集 → DB → プロダクト → SNS → 営業 と直列になって時間がかかる。SHIOKONBU では AI と一緒に、**できるものは同時並行で一気に進める**。

| Track | 分類 | 中身 |
|---|---|---|
| 1 | [B] SEO | 検索需要調査、記事改善、地域ページ改善 |
| 2 | [B] SNS | 投稿企画、コンテンツ制作、認知獲得 |
| 3 | [C] DB | データモデル、内部管理画面 |
| 4 | [D] データ収集 | 実在事業者の情報収集・投入 |
| 5 | [D] ユーザー課題検証 | 検索クエリ・SNS反応・問い合わせから需要分析 |
| 6 | [E] マッチング | 少量のデータでも条件検索を試作 |
| 7 | [E] AI対応 | API・Webアクチュエーションを想定した設計 |
| 8 | [F] 事業検証 | 事業者ニーズ、送客価値、課金可能性の調査 |

「前の作業が100%終わるまで次を始めない」進め方にはしない。各トラックが互いにフィードバックしながら速く回す。

- 5社分のDBができた → その5社で検索UIを試す
- SEOで新しいニーズが見つかった → DB項目へ足す
- SNSで質問が多かった → 記事や条件検索へ反映
- 事業者ヒアリングで新しい条件が出た → DBを直す

**AIに任せる範囲**：調査、データ整理、競合分析、SEO分析、記事企画、SNS企画、DB設計、コーディング、テスト、データ投入、QA、改善案作成まで。人（Nori）は方向性の決定、事業判断、優先順位、最終確認、対外的に人が必要な部分に集中する。

ただし **高速化＝大量生成ではない**。作業の重複、整合しない実装、品質確認なしの公開、SEO記事の無差別な大量生成は避ける。基本思想は **並列化＋自動化＋短い検証サイクル**。
