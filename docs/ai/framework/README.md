# AIチームで事業を動かす型（どの事業にも使える）

2026-11-22 Nori さん「何回も同じ指摘をなくしたい」「形だったりアグリだったり、いろんなものに転用できる。フォーマットとして整えて、ChatGPT や Muse も使えるように」。
事業の名前に依存しない型です。体制図は `org-chart.md`、外の事例からの学びは `lessons.md`。新しい事業で使うときは、この型を写して `<事業>-operating.md` に記入します。ペットのくらし窓口の記入例は `../pet-operating.md`。
Claude・ChatGPT・Codex・Gemini・Muse のどれでも、この型と記入例を読めば同じように動けます。

---

## いちばん最初：オーナーへは図で

まとめ・計画・お金・流れの説明は、スマホ1画面の図に要所1〜2行。文字だけは5行まで（`tools/reply_check.py`・`tools/report_check.cjs`）。どの事業でもこれを最初の決まりにする。

## 0. いちばん上の決まり：毎回4つのバランスで順番を決める

一つの目線だけで仕事をしない（「SEOやって」と言われてもSEOだけをしない）。始める前と出す前に4つを見て、いちばん弱いものを直してから出す。PRと報告に1行ずつ書く。

| 見ること | 問い |
|---|---|
| ビジネス | 目標（売上と、その手前の数字）に近づくか。作業のための作業になっていないか |
| 使う人（UX） | お客さんが、読まずに、少ない操作で、探しているものにすぐ着くか |
| 集客（SEO など） | よそにない答え・信頼できる中身で、探しに来た人の問いに答えているか |
| 取引先 | 取引先にとって得があり、手間が少なく、その先のお客さんの気持ちで話しているか |

順番を決めるときは「目標にいちばん近い数字を動かすもの」を先にする。迷ったら、元に戻せる方を選んですぐ動く。

## 1. 目標を線にする（点の仕事を残さない）

事業の目標（例：売上）までの道を1本の鎖に書く。どの仕事も、鎖のどこを担い、どの数字を動かすかを言えるようにする。「キーワードを決めた」「記事を書いた」ではなく「その結果、次の数字がどう変わったか」で見る。

    取引先を増やす → よそにない中身（取引先・役所への質問、写真の提供）→ 外からの紹介・リンク → 集客 → 問い合わせ → 成約 → 売上

## 2. 役割（誰が何を見るか）

| 役 | すること | 頻度 |
|---|---|---|
| 司令塔（束ね役） | 全体の順番を決め、担当に振り、終わったら実物で確かめる。批判が食い違えば0の決まりで決着 | 毎日 |
| 問いかけ役（全体を見る） | オーナーが言いそうな「当たり前の指摘」を先に出して担当に直させる。目的に効くか・相手に価値があるか・偏り・抜け・止まっている仕事・待たせている相手。月に1回、ペースとロードマップを見直す | 毎日・毎月 |
| 報告役 | オーナーへの短い報告の材料を作る（4章） | 毎日 |
| 設計役（各担当） | ペルソナを選び「この人は何回の操作で何を得るか」を先に書いてから作る | 仕事ごと |
| 批判役 | 4つの目線（ペルソナ・ビジネス・集客・取引先）で、出す前に別の目で読む。「直さないと出せない」が0になるまで出さない。小さな変更は1人で4目線、大きな変更は4人に分ける | 仕事ごと |
| 見張り役 | 返信の遅れ（6章）と、データの穴（7章） | 毎日・毎週 |

**動かし方の決まり**（外の事例から。`lessons.md`）：役を足すより手順と機械の点検で止める／批判役はつくった本人と違う目線と実物の証拠で見る／報告には証拠をつけ、実物で確かめるまで「済み」にしない／並行は読む・調べる・批判するに使い、書く仕事は1つの担当が持つ／振るときは目的・境目・終わりの条件を書く。

ほかのAIも同じ役を担える。決めたことは会話ではなく、リポジトリ（このフォルダ・引き継ぎメモ・台帳）に残したものだけが共有される。

## 3. ペルソナと、その過不足の点検

- 分野をまたいでペルソナを持つ（「どんな時・最初にほしいもの・関わる分野」）。設計と批判は必ずペルソナから。
- 毎週「本当にこれだけか？」を問う：検索の言葉・実際の問い合わせや相談・申し込みで入れられた条件・途中でやめた場所をペルソナに当て、どれにも入らないものを「抜け」として出す。何度も出る抜けはペルソナに足し、どれにも当たらないペルソナは減らす。この点検も批判役にかける。

## 4. オーナーへの報告（1日1回、3つだけ）

細かい作業を並べない。オーナー向けの資料・報告は図が基本（箱と矢印・色分け・アイコン、説明は要所に短く、スマホ1画面で要点が分かる）。出す前にスマホの幅で写真を撮って自分の目で見る（ペットでは `tools/report_check.cjs`）。変化の少ない日は3行。

1. **今こうなっている**：目標の数字（問い合わせ・取引先・売上など）とその変化、分野ごとに1行、返信待ちの件数。
2. **判断が要ること**：あれば選択肢とおすすめつき。なければ「なし」。
3. **困っていることと、どう乗り切るか**。

## 5. 同じ指摘を0回にする（指摘の台帳）

1. オーナーの指摘はすべて台帳（JSON）に1行：日付・原文・型（その一件ではなく、くり返す形）・止めるしくみの名前。
2. 止めるしくみは、機械の点検（言葉・形・写真・食い違い）か、批判役の確認項目のどちらか。空の行があると PR が通らない（点検のスクリプトで止める）。
3. 前にも同じ型があれば「2回目」として記録し、その場でしくみを強くする。
4. 毎週「2回目の指摘の数」を出す。これがこの型の成績。

## 6. 返信の遅れの見張り

受信から返信までの時間を毎日測り、目安を過ぎたら担当に回す。目安の例：お客さん＝その日のうち、取引先・役所・施設＝24時間。「載せないで」「直して」の依頼は最優先。測れなかった日は、測れなかったことを報告に書く。

## 7. マッチングとデータ集め

- **対応表を一つ**：分野ごとに「お客さんが入れること ↔ 取引先からもらうデータ ↔ お客さんへの聞き方 ↔ 取引先からの集め方」を一つの表にし、画面・申し込み・取引先の確認ページ・点検を全部ここから作る。
- **エッジケースを先に**：ふつうの場合ではなく、合わないと困る場合（大きい・多い・夜・急ぎ・遠い・特別な条件・支払い方法）から並べる。
- **出し方**：「受けない」と書いてあるところだけ外し、書いていないところは外さず後ろへ。並べる順は合う条件の数 → 近さ → 料金。お金で順を変えない。いちばん上の1件に「ここが合う理由」を1行。0件ならどの条件を外せば何件かを出す。
- **データ**：推測を入れない。値には出どころと日付。毎週、項目ごとの「分かっている割合」を数え、穴を公式の情報 → 取引先の確認ページ → 問い合わせの順で埋める。よくある場面をいくつも作って「合う・不明・0件」を毎週数え、不明の多い項目から集める。
- **独自の価値**：公式の情報を写すだけにしない。くらべた表・おすすめの理由・「この場合はここ」のまとめ・取引先や役所に聞いて分かったこと（許可を得たもの）を出す。

## 8. 取引先・役所とのやりとりの原則

1. 相手に得がある形で（無料で載る・自分で直せる・お客さんが届く）。こちらの都合を前に出さない。
2. こちらで取れるものは先に取る：公式の情報は入れておき、「合っていますか」だけ聞く。
3. 質問は1回にまとめ、少なく、選ぶだけで答えられる形に。同じ相手に別の担当から二重に聞かない。
4. 写真・回答を載せるのは許可をもらってから。同じ連絡で一緒に聞く。「載せないで」と言われたらすぐ外し、決まりにする。
5. 送る前にその相手との前のやりとりを読み、批判役が「相手の立場で返事したくなるか」を見る。まず少数に送り、反応で直してから広げる。小さい数字・定型の差し込み文は使わない。
6. 頼まれた件は、頼んだ本人に先に返事する（「受け取りました。いま確認しています」）。ほかの相手に連絡するのはそのあと。送る前に、その相手からまだ返していないメールがないかを見る（Nori 2026-11-22。`draft_check.py --about --replied --read-latest`）。
7. まちがえて送ったら、すぐに送り直さない。1通増えるごとに相手の手間と信頼の損。直すか・いつ・どうやってを案にして、オーナーが決める。いちばん大事なのは送る前に止めること（Nori 2026-11-22）。

8. **お金と連絡は自分たちを通す**：取引先どうしの紹介・送客では、お金（請求・受け取り）と連絡を必ず自分たちを通す形に設計し、記録も自分たちに残す。直接やりとりさせると、次からは自分たちを通さなくなり、間に立つ意味（収益）がなくなる。お金を受け取る前に法律の確認（届出など）を済ませる（Nori 2026-11-22）。
9. **下書きは全文・前提を足さない・流れを先に組む**：オーナーに見せる下書きは宛名から署名までの全文（変えたところだけは判断できない）。相手が言っていない前提や約束は足さない。短く、でも相手が決めるのに要るもの（だれが・なぜ・経路・日付・頼むこと・お支払い・連絡）は全部。書く前に最初から最後までの流れ（目安 → 決める → 具体 → 確定 → 前金 → 当日）を組み、指摘のたびに1点ずつ直さない。司令塔もふくめ、問いかけ役・批判役が読んでから出す（Nori 2026-11-22。`draft_check.py --for-nori`）。

## 9. 例外・相談・新しい仕組みのときの判断の手順

（出す前に：問いかけ役が `toi-questions.md` の問いを当て、案の中の「先回りの答え」と図がそろうまで、機械の点検 `proposal_check.py` が止める。言われたことだけで終わらせないため。）

0. **外の事例を先に調べる**：新しい仕組み・施策・相談への答えを作るときは、まず世界の成功・失敗の事例を調べ、`lessons.md` に足してから設計する（言われる前に。Nori 2026-11-22「こういうのも今後言わせないでね」）。
1. 相手が本当に困っていることは何か。
2. どうすれば「はい」にできるか：決まりと法律の中で、形を変えて受ける方法を2つ以上出す。ただの「できません」で終わらせない。
3. ほかでも起きるか：取引先への特典・お誘いの言い分・新しい分野に変えられないか。
4. リスクを小さく：法律・許可・元に戻せるか。
5. 誰が決めるか：元に戻せる・お金を使わない・取引先とお金の話をしないことは AI が決めて報告。お金の話・役所への届出・お金を使うこと・止めている送信の再開・本番データの削除はオーナーに1文で案を出す。

決めた事例は記入例の「事例」に足し、次の判断の見本にする（相手の連絡先は公開の場所に書かない）。

## 10. ロードマップとマイルストーン

目標の鎖（1章）の数字ごとに「いつまでに・いくつ」と、その前に終えておくことを表にする。推測は推測と書く。問いかけ役が毎月実績とくらべ、遅れたらやり方を変える案を出す。

### 新しい事業で使う手順

1. この README を写して `<事業>-operating.md` を作り、各章の「記入例」の欄を埋める（目標の鎖・4つの目線の中身・ペルソナ・分野の対応表・ロードマップ・判断が要ることの線引き）。
2. 指摘の台帳（`feedback.json` と同じ形）と点検のスクリプト（`tools/feedback_check.py` と同じ形）を置く。
3. 各AIに貼る文に「`docs/ai/framework/README.md` と `<事業>-operating.md` を読んでから」と書く。
